## 학습 목표

LoRA(Low-Rank Adaptation)는 큰 pretrained weight를 고정하고, 그 weight에 더할 작은 저랭크 업데이트만 학습하는 parameter-efficient fine-tuning 기법이다. 이 글을 마치면 다음을 할 수 있다.

- PyTorch `Linear`의 weight convention에 맞춰 $W_0$, $A$, $B$의 shape를 정확히 쓴다.
- $operatorname{rank}(BA)\le r$와 trainable parameter 수 $r(d_{\mathrm{in}}+d_{\mathrm{out}})$를 유도한다.
- LoRA scaling $s=\alpha/r$의 역할과 rank를 바꿀 때 생기는 실험 조건 변화를 설명한다.
- $B=0$ 초기화가 첫 forward를 보존하면서 첫 backward의 gradient를 어떻게 여는지 계산한다.
- NumPy 손계산, PyTorch 학습, merge·unmerge 테스트로 구현을 검증한다.
- C++와 C#에서 같은 행렬 계산을 framework 없이 재현한다.
- `NCHW`, `NHWC`, row-major, dtype, transpose convention을 runtime 사이에서 맞춘다.
- optimizer state, activation, quantization, ONNX, adapter 교체 관점의 비용과 실패 모드를 판단한다.

## 선수 지식과 기호

행렬 곱, 행렬 rank, chain rule, `nn.Linear`, optimizer의 기본 동작을 알고 있으면 충분하다. 배치 외에 token이나 공간 축이 있어도 마지막 feature 축에 같은 선형변환을 적용한다고 생각하면 된다.

| 기호 | 뜻 | shape |
| --- | --- | --- |
| $X$ | 입력을 2차원으로 펼친 행렬 | $(M,d_{\mathrm{in}})$ |
| $W_0$ | 고정된 base weight | $(d_{\mathrm{out}},d_{\mathrm{in}})$ |
| $b$ | base bias | $(d_{\mathrm{out}})$ |
| $A$ | 입력을 rank 공간으로 내리는 trainable factor | $(r,d_{\mathrm{in}})$ |
| $B$ | rank 공간을 출력으로 올리는 trainable factor | $(d_{\mathrm{out}},r)$ |
| $r$ | LoRA rank | $r\ll\min(d_{\mathrm{in}},d_{\mathrm{out}})$인 경우가 많음 |
| $\alpha$ | adapter scaling hyperparameter | scalar |
| $s$ | 실제 multiplier | $\alpha/r$ |
| $\Delta W$ | LoRA가 표현하는 weight update | $sBA$ |
| $Y$ | 출력 | $(M,d_{\mathrm{out}})$ |

PyTorch는 `nn.Linear(in_features, out_features)`의 weight를 `(out_features, in_features)`로 저장한다. 따라서 이 글은 column-vector 식 $y=W_0x$와 row-batch 식 $Y=XW_0^\top$을 구분한다.

## 1. 직관: 모델 전체가 아니라 이동 방향의 부분공간을 학습한다

큰 지도를 새로 인쇄하는 대신, 기존 지도 위에 작은 수정 레이어를 얹는다고 생각하자. full fine-tuning은 $W_0$의 모든 원소를 움직일 수 있다. LoRA는 가능한 변화량을 $BA$ 꼴로 제한한다.

1. $A$가 입력 feature를 $r$차원의 작은 좌표로 압축한다.
2. $B$가 그 좌표를 출력 feature 공간으로 다시 펼친다.
3. base 경로의 출력과 adapter 경로의 출력을 더한다.
4. 학습이 끝나면 $sBA$를 $W_0$에 합쳐 하나의 weight로 만들 수도 있다.

중요한 제한은 “원래 weight가 low-rank”라는 뜻이 아니라 **학습으로 허용한 변화량**이 rank $r$ 이하라는 뜻이다. 이 제약이 task에 맞으면 적은 trainable parameter로 충분하고, 맞지 않으면 rank나 target module을 늘려야 한다.

## 2. 원문에서 바로잡을 점

### 2.1 행렬 shape convention을 하나로 고정해야 한다

원문은 $W_0$를 $d\times k$로 둔 뒤 $A$를 $r\times d$, $B$를 $k\times r$로 적어 $BA$가 $k\times d$가 된다. 두 convention이 섞여 그대로는 $W_0+BA$를 계산할 수 없다.

이 글은 PyTorch convention으로 다음과 같이 고정한다.

$$
W_0\in\mathbb{R}^{d_{\mathrm{out}}\times d_{\mathrm{in}}},
\quad
A\in\mathbb{R}^{r\times d_{\mathrm{in}}},
\quad
B\in\mathbb{R}^{d_{\mathrm{out}}\times r}
$$

그러면 $BA$와 $W_0$가 모두 $(d_{\mathrm{out}},d_{\mathrm{in}})$이다.

### 2.2 표준적인 scaling $\alpha/r$가 빠져 있다

원문의 구현은 단순히 $BA$를 더한다. 널리 쓰이는 LoRA 구현은 보통 $s=\alpha/r$를 곱한다.

$$
\Delta W
=
\frac{\alpha}{r}BA
$$

이 scaling은 rank를 바꿨을 때 update 크기가 무조건 같아짐을 보장하지 않는다. 다만 rank와 update scale을 분리해 조절하는 convention을 제공한다. 서로 다른 실험을 비교할 때는 $r$, $\alpha$, learning rate를 함께 기록해야 한다.

### 2.3 weight만 멈추면 base bias는 계속 학습될 수 있다

원문 코드는 `self.linear.weight.requires_grad = False`만 설정한다. `nn.Linear`의 bias는 기본적으로 trainable이므로 “$A$, $B$만 업데이트”라는 설명과 실제 코드가 다르다. base module 전체를 freeze하거나 optimizer에 adapter parameter만 명시해야 한다.

### 2.4 작은 rank가 곧 추상적 스타일을 뜻하지 않는다

$r$은 update가 사용할 수 있는 선형 독립 방향의 상한이다. 작은 $r$이 “추상 스타일”, 큰 $r$이 “세부 묘사”를 각각 담당한다는 보편 법칙은 없다. 적절한 rank는 target layer, dataset, task, regularization에 따라 달라지며 validation과 ablation으로 정해야 한다.

### 2.5 trainable parameter 감소와 총 학습 메모리 감소는 같은 문장이 아니다

LoRA는 trainable gradient와 optimizer state를 크게 줄인다. 그러나 frozen base weight 자체와 forward activation은 여전히 필요하다. base model이 매우 크면 LoRA만으로 device memory에 들어온다는 보장은 없다. quantized base, gradient checkpointing, CPU offload 같은 별도 기법이 필요할 수 있다.

### 2.6 catastrophic forgetting을 자동으로 없애지는 않는다

base checkpoint를 보존하고 adapter를 분리하면 원본 능력으로 돌아가기 쉽다. 하지만 adapter를 켠 상태의 출력은 특정 task에 치우칠 수 있고, 잘못 학습된 adapter는 base 능력을 가릴 수 있다. LoRA는 forgetting을 관찰·복구하기 쉬운 구조이지 모든 간섭을 수학적으로 제거하는 장치는 아니다.

### 2.7 merge하면 추가 matmul은 없어지지만 항상 “100% 동일”하지는 않다

float 수학에서는 $(W_0+sBA)x$와 $W_0x+sBAx$가 같다. 실제 runtime에서는 연산 순서, dtype cast, quantization, kernel이 달라 작은 반올림 차이가 날 수 있다. 여러 adapter를 즉시 교체해야 하면 merge하지 않은 두 matmul 경로를 유지하므로 추가 latency도 남는다.

### 2.8 파일 크기와 데이터 수를 고정값으로 일반화할 수 없다

adapter 크기는 target layer 수, 각 layer shape, rank, 저장 dtype에 의해 결정된다. 특정 이미지 몇 장이면 항상 5MB adapter로 얼굴을 충실히 학습한다는 보장은 없고, 데이터 품질·중복·caption·regularization·base model에 따라 결과와 privacy risk가 달라진다.

## 3. 수학 1: forward와 shape

### 3.1 column-vector 식

한 입력 $x\in\mathbb{R}^{d_{\mathrm{in}}}$에 대한 forward는 다음과 같다.

$$
y
=
W_0x+b+sBAx
$$

연산 순서와 shape를 오른쪽부터 추적하면 다음과 같다.

$$
x
\xrightarrow{A}
Ax\in\mathbb{R}^{r}
\xrightarrow{B}
BAx\in\mathbb{R}^{d_{\mathrm{out}}}
$$

### 3.2 PyTorch row-batch 식

PyTorch 입력의 마지막 축이 `in_features`다. 앞축을 모두 곱해 $M$으로 펼치면 $X\in\mathbb{R}^{M\times d_{\mathrm{in}}}$이고 다음을 계산한다.

$$
Y
=
XW_0^\top+b+s(XA^\top)B^\top
$$

각 중간 shape는 다음과 같다.

$$
(M,d_{\mathrm{in}})
\xrightarrow{A^\top}
(M,r)
\xrightarrow{B^\top}
(M,d_{\mathrm{out}})
$$

예를 들어 ViT attention projection의 입력이 `(2, 128, 768)`, 출력 차원이 768, rank가 8이면 다음과 같다.

| 단계 | 연산 | shape |
| --- | --- | --- |
| 입력 | $X$ | `(2, 128, 768)` |
| rank bottleneck | $XA^\top$ | `(2, 128, 8)` |
| adapter output | $(XA^\top)B^\top$ | `(2, 128, 768)` |
| base output | $XW_0^\top+b$ | `(2, 128, 768)` |
| 최종 합 | base + scaled adapter | `(2, 128, 768)` |

`nn.Linear`는 앞의 `(2, 128)`을 batch-like 축으로 보존하므로 직접 reshape할 필요가 없다.

## 4. 수학 2: 왜 low-rank인가

### 4.1 rank 상한

행렬 곱의 rank에는 다음 부등식이 성립한다.

$$
\operatorname{rank}(BA)
\le
\min(\operatorname{rank}(B),\operatorname{rank}(A))
\le r
$$

따라서 $BA$는 $d_{\mathrm{out}}\times d_{\mathrm{in}}$ 크기여도 독립적인 변화 방향을 최대 $r$개만 표현한다. $r=1$이면 모든 row update가 하나의 공통 입력 방향 $A$를 서로 다른 크기로 사용한다.

### 4.2 parameter 수

full update는 bias를 제외하면 다음 개수의 parameter가 필요하다.

$$
P_{\mathrm{full}}
=
d_{\mathrm{out}}d_{\mathrm{in}}
$$

LoRA의 두 factor는 다음 개수다.

$$
P_{\mathrm{LoRA}}
=
rd_{\mathrm{in}}+d_{\mathrm{out}}r
=
r(d_{\mathrm{in}}+d_{\mathrm{out}})
$$

LoRA parameter 수가 full weight보다 작으려면 다음 조건이 필요하다.

$$
r
<
\frac{d_{\mathrm{out}}d_{\mathrm{in}}}
{d_{\mathrm{in}}+d_{\mathrm{out}}}
$$

$d_{\mathrm{in}}=d_{\mathrm{out}}=768$, $r=8$이면 다음과 같다.

$$
P_{\mathrm{full}}=768^2=589{,}824
$$

$$
P_{\mathrm{LoRA}}=8(768+768)=12{,}288
$$

이 layer의 trainable weight 수만 비교하면 정확히 48배 적다. 전체 모델의 절감률은 LoRA를 어느 module에 붙였는지까지 합산해야 한다.

### 4.3 표현력의 경계

원하는 full-fine-tuning update를 $\Delta W^*$라 하자. $r\ge\operatorname{rank}(\Delta W^*)$이면 적절한 $A$, $B$가 그 update를 정확히 표현할 수 있다. $r$이 더 작으면 일반적으로 근사만 가능하다.

이 사실이 학습 성공을 보장하지는 않는다. optimization이 좋은 factor를 찾는지, 선택한 layer가 task에 충분한지, data가 필요한 update를 식별하는지가 별도 조건이다.

## 5. 수학 3: 초기화와 첫 gradient

보편적인 선택 하나는 $A$를 작은 random 값으로 초기화하고 $B=0$으로 두는 것이다.

$$
A=A_0,
\qquad
B=0
$$

그러면 초기 update와 forward 변화는 정확히 0이다.

$$
\Delta W
=
sBA_0
=
0
$$

### 5.1 $B$의 gradient

adapter 출력만 $Z=sX A^\top B^\top$라 하고 상류 gradient를 $G=\partial\mathcal{L}/\partial Z$라 하자. shape를 유지한 matrix calculus 결과는 다음과 같다.

$$
\frac{\partial\mathcal{L}}{\partial B}
=
sG^\top(XA^\top)
$$

현재 $B=0$이어도 이 식에는 $B$가 곱해지지 않는다. $XA^\top$과 $G$가 0이 아니면 첫 backward에서 $B$는 gradient를 받는다.

### 5.2 $A$의 gradient

반면 $A$의 gradient는 다음과 같다.

$$
\frac{\partial\mathcal{L}}{\partial A}
=
sB^\top G^\top X
$$

첫 backward에는 $B=0$이므로 다음이 성립한다.

$$
\frac{\partial\mathcal{L}}{\partial A}
=
0
$$

첫 optimizer step으로 $B$가 0을 벗어나면 다음 backward부터 $A$에도 gradient가 흐른다. 전날 ControlNet의 zero convolution처럼, zero-initialized 마지막 factor가 forward를 보존하면서 앞 factor의 gradient gate를 한 step 늦게 연다.

### 5.3 둘 다 0으로 초기화하면 안 되는 이유

$A=0$, $B=0$이면 위 두 gradient가 모두 0이므로 학습이 시작되지 않는다. 둘 중 하나는 0, 다른 하나는 nonzero여야 초기 output은 유지하면서 한 factor의 gradient가 열릴 수 있다.

## 6. NumPy 손계산 검증

다음은 **실행 가능한 예제**다. rank 1인 작은 행렬로 분리 경로와 merged weight가 같은 결과를 내는지 확인한다.

```python
import numpy as np

W0 = np.array([
    [1.0, 0.0, 2.0],
    [-1.0, 3.0, 0.5],
])                          # (out=2, in=3)
A = np.array([[0.5, -1.0, 2.0]])  # (rank=1, in=3)
B = np.array([[2.0], [-1.0]])      # (out=2, rank=1)
x = np.array([1.0, 2.0, -1.0])
alpha = 2.0
rank = 1
scale = alpha / rank

rank_feature = A @ x
base = W0 @ x
adapter = scale * (B @ rank_feature)
split_output = base + adapter

delta_w = scale * (B @ A)
merged_output = (W0 + delta_w) @ x

np.testing.assert_allclose(rank_feature, [-3.5])
np.testing.assert_allclose(base, [-1.0, 4.5])
np.testing.assert_allclose(adapter, [-14.0, 7.0])
np.testing.assert_allclose(split_output, [-15.0, 11.5])
np.testing.assert_allclose(merged_output, split_output)
assert np.linalg.matrix_rank(delta_w) <= rank

print("rank_feature:", rank_feature)
print("output:", split_output)
print("rank(delta_w):", np.linalg.matrix_rank(delta_w))
```

손으로도 $Ax=-3.5$, $W_0x=(-1,4.5)^\top$, $sB(Ax)=(-14,7)^\top$이므로 최종 출력은 $(-15,11.5)^\top$이다.

## 7. PyTorch 구현

### 7.1 실행 가능한 `LoRALinear`

다음 구현은 교육용이지만 그대로 실행 가능하다. production library가 다루는 adapter registry, distributed sharding, quantized base, tied weight까지 포함한 완전한 대체품은 아니다.

```python
import math
import torch
from torch import nn
from torch.nn import functional as F


class LoRALinear(nn.Module):
    def __init__(
        self,
        in_features: int,
        out_features: int,
        rank: int = 8,
        alpha: float = 8.0,
        bias: bool = True,
    ) -> None:
        super().__init__()
        if rank <= 0:
            raise ValueError("rank must be positive")

        self.in_features = in_features
        self.out_features = out_features
        self.rank = rank
        self.scale = alpha / rank

        self.weight = nn.Parameter(
            torch.empty(out_features, in_features),
            requires_grad=False,
        )
        if bias:
            self.bias = nn.Parameter(
                torch.empty(out_features),
                requires_grad=False,
            )
        else:
            self.register_parameter("bias", None)

        self.lora_a = nn.Parameter(torch.empty(rank, in_features))
        self.lora_b = nn.Parameter(torch.zeros(out_features, rank))
        self.register_buffer("merged", torch.tensor(False), persistent=False)

        nn.init.kaiming_uniform_(self.weight, a=math.sqrt(5))
        nn.init.kaiming_uniform_(self.lora_a, a=math.sqrt(5))
        if self.bias is not None:
            bound = 1 / math.sqrt(in_features)
            nn.init.uniform_(self.bias, -bound, bound)

    @classmethod
    def from_linear(
        cls,
        base: nn.Linear,
        rank: int,
        alpha: float,
    ) -> "LoRALinear":
        layer = cls(
            base.in_features,
            base.out_features,
            rank=rank,
            alpha=alpha,
            bias=base.bias is not None,
        ).to(device=base.weight.device, dtype=base.weight.dtype)
        with torch.no_grad():
            layer.weight.copy_(base.weight)
            if base.bias is not None:
                layer.bias.copy_(base.bias)
        return layer

    def delta_weight(self) -> torch.Tensor:
        return self.scale * (self.lora_b @ self.lora_a)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        output = F.linear(x, self.weight, self.bias)
        if not bool(self.merged):
            output = output + self.scale * F.linear(
                F.linear(x, self.lora_a),
                self.lora_b,
            )
        return output

    @torch.no_grad()
    def merge(self) -> None:
        if not bool(self.merged):
            self.weight.add_(self.delta_weight().to(self.weight.dtype))
            self.merged.fill_(True)

    @torch.no_grad()
    def unmerge(self) -> None:
        if bool(self.merged):
            self.weight.sub_(self.delta_weight().to(self.weight.dtype))
            self.merged.fill_(False)
```

`merged`는 Python bool이 아니라 buffer scalar다. 이 교육용 선택은 eager mode에서는 충분하지만 export 전에 분기를 제거하고 merged 또는 unmerged graph 하나로 고정하는 편이 안전하다.

### 7.2 실행 가능한 학습·shape·gradient 테스트

아래 블록은 위 클래스 정의 뒤에 이어서 실행한다.

```python
torch.manual_seed(7)

base = nn.Linear(6, 4)
layer = LoRALinear.from_linear(base, rank=2, alpha=4.0)
x = torch.randn(3, 5, 6)
target = torch.randn(3, 5, 4)

# B=0이므로 초기 output은 base와 같다.
with torch.no_grad():
    expected = base(x)
    actual = layer(x)
torch.testing.assert_close(actual, expected)
assert actual.shape == (3, 5, 4)

trainable = {name for name, p in layer.named_parameters() if p.requires_grad}
assert trainable == {"lora_a", "lora_b"}

optimizer = torch.optim.SGD(
    [layer.lora_a, layer.lora_b],
    lr=0.1,
)

# 첫 backward: B는 gradient를 받고 A의 gradient는 0이다.
loss = F.mse_loss(layer(x), target)
loss.backward()
assert layer.lora_b.grad is not None
assert layer.lora_b.grad.norm().item() > 0.0
assert layer.lora_a.grad is not None
torch.testing.assert_close(
    layer.lora_a.grad,
    torch.zeros_like(layer.lora_a.grad),
)
optimizer.step()
optimizer.zero_grad(set_to_none=True)

# B가 0을 벗어난 다음 backward에는 A도 gradient를 받는다.
second_loss = F.mse_loss(layer(x), target)
second_loss.backward()
assert layer.lora_a.grad is not None
assert layer.lora_a.grad.norm().item() > 0.0
optimizer.step()
optimizer.zero_grad(set_to_none=True)

# 분리 경로와 merge 경로가 허용 오차 안에서 같다.
with torch.no_grad():
    split = layer(x)
    base_before_merge = layer.weight.detach().clone()
    layer.merge()
    merged = layer(x)
    torch.testing.assert_close(merged, split, rtol=1e-5, atol=1e-6)
    layer.unmerge()
    torch.testing.assert_close(layer.weight, base_before_merge)
    torch.testing.assert_close(layer(x), split, rtol=1e-5, atol=1e-6)

full_count = layer.in_features * layer.out_features
lora_count = sum(
    p.numel()
    for name, p in layer.named_parameters()
    if name.startswith("lora_")
)
assert full_count == 24
assert lora_count == 20

print("shape:", tuple(split.shape))
print("first loss:", round(loss.item(), 6))
print("second loss:", round(second_loss.item(), 6))
print("full/lora parameter count:", full_count, lora_count)
```

이 작은 `(4, 6)` weight에 rank 2를 붙이면 LoRA parameter가 20개라 full weight 24개와 차이가 작다. LoRA의 절감 효과는 큰 matrix와 작은 rank에서 커진다는 사실도 테스트가 보여 준다.

### 7.3 optimizer와 checkpoint 계약

안전한 학습 설정은 `requires_grad`만 믿지 않고 optimizer 입력도 adapter로 제한한다.

```python
# 설명용 코드: 실제 모델의 이름 규칙에 맞춰 필터를 조정한다.
adapter_params = [
    parameter
    for name, parameter in model.named_parameters()
    if "lora_" in name
]
optimizer = torch.optim.AdamW(adapter_params, lr=1e-4)
```

checkpoint에는 최소한 다음 metadata가 필요하다.

- base model identifier와 revision 또는 hash
- target module의 정확한 이름
- 각 module의 `in_features`, `out_features`, rank
- $\alpha$와 scaling convention
- $A$, $B$의 orientation과 dtype
- base bias를 학습했는지 여부
- preprocessing, tokenizer 또는 image normalization revision

작은 adapter 파일만 있어도 다른 base revision에 잘못 붙이면 shape가 같아 조용히 실행되면서 품질만 망가질 수 있다. shape 검사만으로는 부족하므로 base hash를 확인한다.

## 8. C++ 예제

다음은 **실행 가능한 C++17 예제**다. 외부 library 없이 NumPy 예제와 같은 rank 1 update를 계산하고 merge 동등성을 검사한다.

```cpp
#include <array>
#include <cassert>
#include <cmath>
#include <iomanip>
#include <iostream>

int main() {
    constexpr int kIn = 3;
    constexpr int kOut = 2;
    constexpr int kRank = 1;
    const double scale = 2.0;

    const std::array<std::array<double, kIn>, kOut> w0{{
        {{1.0, 0.0, 2.0}},
        {{-1.0, 3.0, 0.5}},
    }};
    const std::array<std::array<double, kIn>, kRank> a{{
        {{0.5, -1.0, 2.0}},
    }};
    const std::array<std::array<double, kRank>, kOut> b{{
        {{2.0}},
        {{-1.0}},
    }};
    const std::array<double, kIn> x{{1.0, 2.0, -1.0}};

    std::array<double, kRank> rank_feature{};
    for (int q = 0; q < kRank; ++q) {
        for (int i = 0; i < kIn; ++i) {
            rank_feature[q] += a[q][i] * x[i];
        }
    }

    std::array<double, kOut> split{};
    std::array<std::array<double, kIn>, kOut> merged = w0;
    for (int o = 0; o < kOut; ++o) {
        for (int i = 0; i < kIn; ++i) {
            split[o] += w0[o][i] * x[i];
            for (int q = 0; q < kRank; ++q) {
                merged[o][i] += scale * b[o][q] * a[q][i];
            }
        }
        for (int q = 0; q < kRank; ++q) {
            split[o] += scale * b[o][q] * rank_feature[q];
        }
    }

    std::array<double, kOut> merged_output{};
    for (int o = 0; o < kOut; ++o) {
        for (int i = 0; i < kIn; ++i) {
            merged_output[o] += merged[o][i] * x[i];
        }
        assert(std::abs(merged_output[o] - split[o]) < 1e-12);
    }

    assert(std::abs(split[0] + 15.0) < 1e-12);
    assert(std::abs(split[1] - 11.5) < 1e-12);
    std::cout << std::fixed << std::setprecision(1)
              << split[0] << " " << split[1] << "\n";
}
```

실제 high-performance C++에서는 작은 두 GEMM을 BLAS, oneDNN, cuBLAS 등으로 실행하거나 weight를 미리 merge한다. raw pointer layout과 BLAS transpose flag를 문서화하지 않으면 수학상 맞는 weight가 전치되어 적용될 수 있다.

## 9. C# 예제

다음은 **실행 가능한 C# 예제**다. C++와 같은 golden output을 계산한다.

```csharp
using System;

public static class Program
{
    public static void Main()
    {
        double[,] w0 = {
            { 1.0, 0.0, 2.0 },
            { -1.0, 3.0, 0.5 }
        };
        double[,] a = { { 0.5, -1.0, 2.0 } };
        double[,] b = { { 2.0 }, { -1.0 } };
        double[] x = { 1.0, 2.0, -1.0 };
        double scale = 2.0;

        int outFeatures = w0.GetLength(0);
        int inFeatures = w0.GetLength(1);
        int rank = a.GetLength(0);
        double[] rankFeature = new double[rank];
        double[] split = new double[outFeatures];
        double[,] merged = (double[,])w0.Clone();

        for (int q = 0; q < rank; q++)
            for (int i = 0; i < inFeatures; i++)
                rankFeature[q] += a[q, i] * x[i];

        for (int o = 0; o < outFeatures; o++)
        {
            for (int i = 0; i < inFeatures; i++)
            {
                split[o] += w0[o, i] * x[i];
                for (int q = 0; q < rank; q++)
                    merged[o, i] += scale * b[o, q] * a[q, i];
            }
            for (int q = 0; q < rank; q++)
                split[o] += scale * b[o, q] * rankFeature[q];
        }

        for (int o = 0; o < outFeatures; o++)
        {
            double mergedOutput = 0.0;
            for (int i = 0; i < inFeatures; i++)
                mergedOutput += merged[o, i] * x[i];
            if (Math.Abs(mergedOutput - split[o]) >= 1e-12)
                throw new Exception("merge mismatch");
        }

        if (Math.Abs(split[0] + 15.0) >= 1e-12 ||
            Math.Abs(split[1] - 11.5) >= 1e-12)
            throw new Exception("golden output mismatch");

        Console.WriteLine($"{split[0]:F1} {split[1]:F1}");
    }
}
```

Unity, ML.NET, ONNX Runtime C# binding에서 adapter를 별도 실행할 때도 배열이 row-major인지, tensor logical shape가 무엇인지, runtime이 내부 transpose를 수행하는지 각각 확인해야 한다.

## 10. framework 간 shape·layout·dtype 대응

| 환경 | base weight의 논리 shape | 입력과 계산 | 주의점 |
| --- | --- | --- | --- |
| PyTorch `nn.Linear` | `(out, in)` | `X @ W.T` | `A=(r,in)`, `B=(out,r)`가 자연스럽다. |
| NumPy 예제 | `(out, in)` | column vector에는 `W @ x` | row batch라면 `X @ W.T`로 바꾼다. |
| C++ 예제 | `w0[out][in]` | 명시 loop | BLAS API의 row-major·column-major와 transpose flag를 확인한다. |
| C# 예제 | `double[out, in]` | 명시 loop | managed multidimensional array는 inference tensor buffer와 성능 특성이 다르다. |
| ONNX `Gemm` | initializer에 따라 다름 | `transB`가 핵심 | export된 graph의 initializer shape와 attribute를 직접 검사한다. |
| image tensor | 보통 `NCHW` 또는 `NHWC` | LoRA 대상 projection 전 feature layout에 의존 | `Linear`는 마지막 축, `Conv2d`는 channel 축을 사용한다. |

### 10.1 convolution에 붙일 때

$k_h\times k_w$ convolution weight는 `(C_out, C_in, k_h, k_w)`다. 이를 단순히 `(C_out, C_in k_h k_w)`로 펼쳐 low-rank update를 만들 수 있지만, 실제 factorized convolution이 공간 kernel과 channel을 어떤 순서로 계산하는지는 구현마다 다르다.

`1x1` convolution은 linear projection과 대응이 단순하지만, 일반 kernel에서는 다음이 서로 같은 adapter라고 가정하면 안 된다.

- flattened kernel 전체를 low-rank factorization
- `k x k` down projection 뒤 `1x1` up projection
- `1x1` down projection 뒤 `k x k` up projection

checkpoint metadata에 factor의 kernel shape와 적용 순서를 포함해야 한다.

### 10.2 dtype

base가 `float16`, adapter가 `float32`이면 forward마다 암묵 cast가 생기거나 연산이 실패할 수 있다. 학습에서는 adapter parameter와 optimizer master weight dtype을 구분하고, merge할 때 $BA$를 어느 dtype으로 계산한 뒤 어느 dtype에 저장했는지 기록한다.

작은 update를 `float16` base에 바로 더하면 일부 원소가 반올림으로 사라질 수 있다. 검증할 때 parameter equality보다 output tolerance와 task metric을 함께 본다.

## 11. 테스트와 디버깅

### 11.1 최소 단위 테스트

- adapter 초기화 직후 base output과 LoRA output이 허용 오차 안에서 같은가?
- trainable parameter 이름이 의도한 `lora_a`, `lora_b`뿐인가?
- optimizer parameter group에 frozen base가 들어가지 않았는가?
- 첫 backward에서 $B$ gradient는 nonzero이고 $A$ gradient는 0인가?
- 한 step 뒤 $A$ gradient도 nonzero가 되는가?
- 임의 leading dimension의 입력에서 마지막 shape만 `out_features`로 바뀌는가?
- merge 전후 output이 허용 오차 안에서 같은가?
- unmerge 후 base weight가 복구되는가?
- 같은 adapter를 두 번 merge하거나 unmerge해도 중복 가감하지 않는가?
- 잘못된 base revision, target name, rank, factor shape를 load 시점에 거부하는가?

### 11.2 자주 보이는 증상과 원인

| 증상 | 가능성 높은 원인 | 확인 방법 |
| --- | --- | --- |
| 초기 output이 base와 다름 | $B$가 0이 아님, scaling 경로 오류, base 복사 실패 | `delta_weight().abs().max()`와 state dict 비교 |
| loss가 전혀 줄지 않음 | $A$, $B$ 모두 0, optimizer 누락, graph detach | gradient norm과 optimizer parameter ID 확인 |
| base checkpoint가 바뀜 | base bias가 trainable, weight decay 대상 포함, 잘못된 merge 저장 | 학습 전후 base tensor hash 비교 |
| shape mismatch | $A$, $B$ 전치, 다른 target module checkpoint | `(out,in)`, `(r,in)`, `(out,r)` assertion |
| merge 후 품질 급락 | scaling 중복, dtype 반올림, quantized weight에 직접 merge | unmerged output과 layer별 오차 비교 |
| adapter를 꺼도 결과가 다름 | 이미 weight에 merge됨, unmerge 중복·누락 | merged state와 base hash 확인 |
| 학습은 되지만 효과가 약함 | rank 부족, target module 부족, data 또는 learning rate 문제 | rank·target layer ablation |
| 여러 adapter 조합이 불안정 | update scale 충돌, 서로 다른 base revision | adapter별 norm과 조합 순서·가중치 기록 |

### 11.3 merge 테스트의 tolerance

`float64`의 작은 예제는 매우 엄격한 tolerance를 쓸 수 있다. GPU `float16` 또는 `bfloat16`에서는 reduction 순서와 tensor core 때문에 더 큰 차이가 자연스럽다. tolerance를 무작정 넓히지 말고 다음 순서로 진단한다.

1. CPU `float32`에서 논리 오류를 제거한다.
2. layer 하나에서 split·merged output 최대 오차를 측정한다.
3. dtype별 tolerance를 근거와 함께 정한다.
4. end-to-end metric과 representative input에서 영향도를 확인한다.

## 12. 성능·메모리·수치 안정성

### 12.1 무엇이 줄어드는가

AdamW가 trainable parameter마다 gradient와 두 moment를 유지한다고 단순화하면 optimizer 관련 storage는 parameter 수에 비례한다. full weight 대신 $A$, $B$만 학습하면 이 부분이 크게 줄어든다.

그러나 다음은 남는다.

- frozen base weight storage
- base forward의 activation과 kernel workspace
- adapter 중간값 $XA^\top$ activation
- loss와 trainable adapter로 gradient를 전달하기 위한 graph
- distributed training의 communication 및 sharding metadata

따라서 “trainable parameter 48배 감소”를 “전체 VRAM 48배 감소”로 바꾸어 말하면 안 된다.

### 12.2 unmerged latency

base linear의 곱셈량을 대략 $Md_{\mathrm{in}}d_{\mathrm{out}}$라 하면 adapter의 추가 곱셈량은 다음과 같다.

$$
Mrd_{\mathrm{in}}+Mrd_{\mathrm{out}}
$$

상대 비율은 parameter 비율과 같은 형태다.

$$
\frac{r(d_{\mathrm{in}}+d_{\mathrm{out}})}
{d_{\mathrm{in}}d_{\mathrm{out}}}
$$

하지만 작은 GEMM 두 개는 hardware utilization과 kernel launch overhead가 나빠 이 비율만큼만 느려진다고 단정할 수 없다. 실제 batch, sequence length, device에서 benchmark한다.

### 12.3 repeated merge·unmerge

낮은 precision weight에 같은 $\Delta W$를 반복해서 더하고 빼면 반올림 오차가 누적될 수 있다. 운영 시스템에서는 다음 중 하나를 택한다.

- immutable base weight를 보관하고 merge weight를 새로 계산한다.
- adapter를 별도 경로로 유지한다.
- 높은 precision master base에서 merge한 뒤 serving dtype으로 한 번 cast한다.

### 12.4 rank와 scaling ablation

공정한 비교를 위해 최소한 다음을 표로 남긴다.

| 실험 축 | 예시 | 함께 고정하거나 기록할 항목 |
| --- | --- | --- |
| rank | 4, 8, 16 | $\alpha$, learning rate, seed |
| target | `q`, `v`, `qkv`, MLP | 총 trainable parameter 수 |
| scaling | $\alpha/r$ 변화 | adapter output norm |
| initialization | $A$ random·$B=0$ | initializer 분포와 seed |
| dtype | FP32, BF16, FP16 | loss scaling, merge dtype |
| regularization | dropout, weight decay | train/eval mode |

validation metric뿐 아니라 base task regression, latency, peak memory, checkpoint size도 함께 측정한다.

## 13. 이미지 모델에서의 target 선택

### 13.1 ViT와 diffusion attention

attention block에는 query, key, value, output projection과 MLP가 있다. 모든 projection에 무조건 adapter를 붙일 필요는 없다.

- `q`, `v`만 적용하면 parameter가 적고 흔한 baseline이 된다.
- `q`, `k`, `v`, output까지 넓히면 표현력과 비용이 함께 늘어난다.
- MLP까지 적용하면 channel transformation을 더 직접 바꿀 수 있다.
- fused `qkv` weight는 slice별 adapter인지 전체 fused matrix adapter인지 checkpoint convention을 명확히 해야 한다.

### 13.2 CNN

ConvNeXt의 pointwise projection은 channel-last `Linear` 또는 `1x1 Conv2d`로 구현될 수 있다. 논리적으로 비슷해도 state dict weight shape는 각각 `(out,in)`과 `(out,in,1,1)`이다. architecture 이름만 보고 adapter를 load하지 말고 module type과 exact shape를 확인한다.

### 13.3 실패를 해석하는 순서

rank를 먼저 크게 올리기 전에 다음을 확인한다.

1. 올바른 module에 실제로 adapter가 연결되었는가?
2. input normalization과 label mapping이 base model과 같은가?
3. adapter gradient와 update norm이 유한하고 nonzero인가?
4. train data에는 좋아지지만 validation에는 나빠지는가?
5. target layer 확장과 rank 증가 중 어느 쪽이 parameter당 이득이 큰가?

## 14. 배포 관점

### 14.1 merged artifact

장점은 inference graph가 원래 linear 또는 convolution 하나로 남아 추가 adapter op가 없다는 것이다. ONNX export와 engine optimization도 단순해질 수 있다.

단점은 adapter마다 전체 merged model artifact가 필요하고 즉시 교체가 어렵다는 것이다. base와 adapter의 분리 배포가 주는 저장 이점도 줄어든다.

### 14.2 dynamic adapter graph

base output과 $sBA$ 경로를 graph에 함께 남기면 작은 adapter만 바꿀 수 있다. 대신 runtime이 작은 GEMM을 효율적으로 실행해야 하고, rank·target shape가 engine build 시 고정될 수 있다.

ONNX export 뒤에는 graph를 이름만 보고 믿지 말고 다음을 확인한다.

- initializer의 실제 shape와 dtype
- `MatMul` 또는 `Gemm`의 transpose convention
- scaling이 정확히 한 번만 적용되는지
- dynamic batch·token·image size 계약
- constant folding이 adapter를 의도치 않게 고정하지 않았는지

### 14.3 quantized base와 QLoRA 계열

quantized base weight에 floating-point $BA$를 정수 tensor처럼 바로 더할 수는 없다. 일반적인 학습은 base weight를 연산 시 dequantize해 adapter output과 더하고, adapter는 higher precision으로 유지한다.

배포 시 선택지는 다음과 같다.

- quantized base와 adapter를 분리 실행
- base를 dequantize해 merge한 뒤 다시 calibration·quantization
- runtime이 지원하는 fused quantized-base-plus-adapter kernel 사용

재양자화는 추가 오차를 만들므로 unmerged reference와 metric을 다시 비교한다.

### 14.4 운영과 모니터링

request log에는 개인정보를 저장하지 않는 범위에서 base revision, adapter ID, adapter revision, scale, preprocessing revision을 남긴다. 다음 metric을 adapter별로 분리한다.

- task quality 또는 사용자 feedback
- base-only 대비 regression
- p50·p95 latency와 peak memory
- NaN·Inf, saturation, output norm drift
- load 실패와 base hash mismatch 횟수

문제가 생기면 adapter를 끄는 것만으로 immutable base 경로로 되돌릴 수 있어야 한다.

## 15. 실무 실패 사례

### 사례 1: 학습했다고 생각했지만 bias만 바뀌었다

base weight만 freeze하고 bias는 그대로 둔 채, `lora_` parameter를 optimizer에 넣지 않았다. loss는 조금 줄어 “LoRA가 학습됐다”고 오판했지만 실제로는 base bias만 변경됐다.

**예방:** trainable parameter 이름·개수와 optimizer parameter ID를 학습 시작 전에 assertion으로 고정한다.

### 사례 2: 다른 base revision에 조용히 load됐다

target layer shape가 같아 adapter load는 성공했지만 base checkpoint가 달랐다. exception은 없고 품질만 크게 떨어졌다.

**예방:** base repository 이름만 저장하지 말고 immutable revision 또는 weight hash를 adapter manifest에 넣는다.

### 사례 3: scaling을 두 번 곱했다

checkpoint가 이미 scaled $B$를 저장했는데 serving loader가 다시 $\alpha/r$를 곱했다. shape와 finite check는 모두 통과했지만 update norm이 과도해졌다.

**예방:** checkpoint가 raw factors인지 pre-scaled factors인지 schema에 명시하고 layer별 $\lVert\Delta W\rVert_F$를 reference와 비교한다.

### 사례 4: FP16 merge·unmerge 반복으로 base가 변했다

여러 adapter를 바꾸면서 동일 FP16 weight에 add와 subtract를 반복했다. 나중에는 adapter를 꺼도 immutable base output과 차이가 났다.

**예방:** 원본 base를 불변으로 보관하고 각 merged artifact를 새로 생성한다.

### 사례 5: fused `qkv` slice 순서를 잘못 해석했다

checkpoint는 `q,k,v` 순서였지만 serving code가 `q,v,k`로 slice했다. tensor shape는 같아 load되었고 품질만 붕괴했다.

**예방:** module 이름뿐 아니라 fused layout, slice offset, orientation을 manifest와 golden input-output test로 고정한다.

## 17. 연습문제

### 문제 1

$d_{\mathrm{in}}=1024$, $d_{\mathrm{out}}=4096$, $r=16$일 때 full weight와 LoRA의 parameter 수, 절감 배수를 구하라. bias는 제외한다.

### 문제 2

$A=0$, $B=0$으로 동시에 초기화하면 왜 첫 optimizer step이 adapter를 움직이지 못하는가?

### 문제 3

입력 shape가 `(N, C, H, W)=(2, 64, 14, 14)`이고 channel마다 마지막 축 linear를 적용하려고 `NHWC`로 바꾼 뒤 `Linear(64, 128)`과 rank 4 LoRA를 사용한다. rank bottleneck과 출력 shape를 각각 쓰라.

### 문제 4

base가 FP16이고 adapter가 FP32일 때 merge를 안전하게 수행하는 절차 하나를 제안하라.

### 문제 5

LoRA checkpoint의 tensor shape가 target module과 일치했다. 이것만으로 올바른 adapter라고 결론내릴 수 없는 이유 두 가지를 쓰라.

## 18. 해답

### 해답 1

full weight는 다음과 같다.

$$
1024\times4096
=
4{,}194{,}304
$$

LoRA는 다음과 같다.

$$
16(1024+4096)
=
81{,}920
$$

따라서 trainable weight 수는 약 $4{,}194{,}304/81{,}920=51.2$배 적다.

### 해답 2

$\partial\mathcal{L}/\partial B$에는 $XA^\top$이 들어가므로 $A=0$이면 0이다. $\partial\mathcal{L}/\partial A$에는 $B$가 들어가므로 $B=0$이면 0이다. 두 factor의 gradient가 모두 0이어서 symmetry를 깨고 출발할 nonzero 경로가 없다.

### 해답 3

`NCHW -> NHWC` 뒤 입력은 `(2, 14, 14, 64)`다. 마지막 축을 $A^\top$에 곱한 rank bottleneck은 `(2, 14, 14, 4)`, $B^\top$까지 적용한 출력은 `(2, 14, 14, 128)`이다. 다시 `NCHW`로 돌리면 `(2, 128, 14, 14)`다.

### 해답 4

immutable FP32 base master를 준비하고 $BA$도 FP32에서 계산해 scaling과 merge를 수행한다. merged FP32 reference output을 만든 뒤 serving FP16으로 한 번 cast하고, split FP32·merged FP32·merged FP16의 오차와 task metric을 단계적으로 비교한다.

### 해답 5

첫째, shape가 같은 다른 base revision일 수 있다. 둘째, $A$, $B$ orientation이나 fused `qkv` slice 순서와 scaling convention이 다를 수 있다. 따라서 base hash, target name, layout, $\alpha/r$ metadata와 golden output이 필요하다.

## 핵심 요약

1. PyTorch convention에서 $W_0$와 $BA$는 `(out, in)`, $A$는 `(r, in)`, $B$는 `(out, r)`다.
2. LoRA update는 보통 $\Delta W=(\alpha/r)BA$이며 rank는 변화량의 독립 방향 수를 제한한다.
3. trainable parameter 수는 $r(d_{\mathrm{in}}+d_{\mathrm{out}})$지만 전체 VRAM이 같은 비율로 줄지는 않는다.
4. $A$ random·$B=0$ 초기화는 첫 output을 보존하고, 첫 step에는 $B$, 다음 step부터 $A$의 gradient를 연다.
5. base weight뿐 아니라 bias와 optimizer parameter group도 freeze 계약에 포함해야 한다.
6. merge는 추가 adapter matmul을 없앨 수 있지만 dtype·quantization·반복 가감 때문에 bitwise 동일성을 보장하지 않는다.
7. adapter artifact에는 base hash, target module, rank, scaling, layout, dtype을 함께 저장해야 한다.
8. rank보다 먼저 연결된 module, gradient, preprocessing, scaling, base revision을 검증한다.
